### 1. `fwid` / `hwid` を廃止する

`drop_features` に渡す（`pwid` / `palt` / `kern` / `halt` と同じ扱い）。
併せて `stretch_arrows`(68 行)、`add_width_alternates`(15 行)、
`check_width_forms`(55 行)、`build_face` 内の fwid_map 組み立て、
散在する 41 箇所、門番 4〜5 本を削除。**コード約 250 行**。

**根拠**: この機能は狙っている用途では呼び出せません。VS Code などは
font feature をエディタ全体にしか適用できず、`fwid` を有効にすると
621 組すべてが発火して `A` が `Ａ` になる。「全角の罫線だけ欲しい」が
構造的に不可能。ターミナルはそもそも feature を適用しません。
Adobe の Source Han Code JP も持っておらず、Moralerspace は同じ需要に
**別フォントファイル**（JPDOC）で応えています。

**期待しないこと**: ファイルは縮みません。fwid 専用グリフ 264 個のうち
**ビルドが描いたのは 7 個だけ**で、257 個は Source Han Sans 由来。
孤立グリフを刈る仕組みはこのビルドに無いので、CFF には残ります。

**将来「記号を全角に」をやるなら**、feature ではなく JPDOC と同じく
バリエーションとして、`WIDE_IN_ONE_CELL` などの方針表で。新しい仕組みは
要りません。

#### 結果（済）

- `drop_features` に `fwid` / `hwid` を渡し、`stretch_arrows`・
  `stretch_path`・`fullwidth_forms`・`add_width_alternates`・`build_face` の
  配線を削除。**見積もりに無かった分**: `tile_vertically` /
  `vtiling_glyphs`（`fwid` で届く全角罫線だけを縦に伸ばす処理で、`fwid` が
  無いと常に 0 件になる）と `tiling_glyphs` の `fwid` の枝も削除した
- 門番: `fwid` の全角形だけを見るもの（`fwid` の形・矢印・線の端・角丸・
  ブロック要素）は削除、既定形と両方を見ていたもの（タイル・罫線が描く・
  破線・縦罫）は既定形の側を残し、「GSUB に fwid / hwid がある」は
  「無い」に反転。`check_width_forms` は `vert` の半分だけ残して
  `check_vertical_forms` に
- **示したこと**: main で組んだ全 62 面と比べ、`golden.py`（main 側の、
  `fwid` / `hwid` の整形も見る版）の差分は「GSUB の tag から fwid / hwid が
  消えた」と「`[fwid]` / `[hwid]` の下の整形」だけ。cmap・送り幅・
  アウトライン・メタデータ・既定の整形は全面で一致し、欧文の静的 10 面・
  可変 2 本・欧文 NF 10 面はヒント以外すべて一致。全面の検証は FAIL が

- **実測**: `fwid` の行き先 364 個のうち消えたのは 7 個（矢印）。残る 357 個は
  `aalt` から 107、cmap から 100、どこからも届かない 250（Regular）。
  `hwid` の 115 個は `aalt` から 98、届かない 15。見積もりどおりファイルは縮まない

### 3. 欧文の可変フォントを残し、メインに押し出す

**根拠**: **このプロジェクトで唯一、他では手に入らない成果物**です。
Source Code Pro の可変版も Monaspace の可変版もありますが、「SCP に
Monaspace の合字を載せた可変フォント」は他に無い。JP 面や NF 版は既存の
合成ツールでも作れます。欧文コーディングフォントの同業（ドナー自身を含む）は
みな可変フォントを出しており、JP コーディングフォントの同業（可変なし）とは
比較対象が違います。

### 4. Nerd Fonts 版の可変フォントを作る（新規）

**実測した結論: 可能。しかも思ったより簡単。**

```
Regular vs Light       : 輪郭が違うアイコン 0 / 10396
Regular vs Bold        : 輪郭が違うアイコン 0 / 10396
Regular vs LightItalic : 輪郭が違うアイコン 0 / 10396
Regular vs BoldItalic  : 輪郭が違うアイコン 0 / 10396
```

アイコン 10,396 個は**ウェイトでも斜体でもバイト単位で同一**（Powerline の
差し替え分 U+E0A0–E0B3 を含む）。だから可変フォントには**変化しない
グリフ**として置けばよく、blend 演算子も VarStore の項目も要りません。

好都合な事実:
- 我々の VF は **HVAR を持たない**（等幅で送りが変化しないため）。
  アイコンも 600 固定なので送りの変化データが不要
- `post` v2 でグリフ名を持っているので、名前つきグリフを足せる
- CFF2 への変換は `T2CharStringPen(..., CFF2=True)` で通る（確認済み）
- サイズは 1,333 KB ＋ 約 2 MB ＝ **約 3.3 MB**（JP 面は 1 枚 4.6 MB）

`nerdpatch.py` は幾何（`icon_transform`、`icon_context`、倍率、Powerline の
描き直し）も門番（`icon_checks`）も**すでに全部持っています**。新規は
**CFF から CFF2 への append 経路だけ**で、おそらく 100〜200 行。

**着手前にスパイクで潰すこと（2 点）**:
1. CFF2 の FDArray / FDSelect への追加が素直にいくか（静的面の
   `add_latin_fd` と筋は同じだが CFF2 は構造が違う）
2. FreeType / HarfBuzz / DirectWrite が「CFF2 に 10,400 個の非変化グリフ」を
   嫌がらないか

できれば `GengouCode.zip` が可変のみ・`GengouCode-NerdFont.zip` が静的のみという
**現在の不整合も解消**します（可変で欲しい人がアイコンを諦める状態）。

#### 結果（済）

- **スパイク**: 1 は素直にいった（FDSelect があれば伸ばし、無い CFF2 は
  FD 0 で書く。`build.append_context` / `append_glyph` / `glyph_fd` を
  CFF2 でも通るようにした）。2 は **FreeType 2.13.2 と HarfBuzz で確認**:
  wght 300 と 700 でアイコンの外接箱もインク量も同一、`A` だけが太さで
  変わる。fontTools の instancer も通る。**DirectWrite はこの環境では
  試せていない**（可変の `GengouCode.zip` がすでに主力なので、グリフが
  増える以外に新しい種類のリスクは無いと判断した）
- `nerdpatch.py` が CFF2 に接ぎ木する: アイコンは幅もブレンドも持たない
  CFF2 の charstring、Powerline は差し替え、`nameID 25`（`GengouCode` →
  `GengouCodeNF`）も書き換え、出力名は `GengouCodeNF[wght].otf` /
  `GengouCodeNF-Italic[wght].otf`。箱は全マスターの和なので「アイコンの分
  だけ広げる」だけにした（差し替えた Powerline の旧い形の分は縮めない。
  広めに残るのはクリップ境界として安全側）。autohint とサブルーチン化は
  しない（`build_latin_vf.py` と同じ）
- **配布の形を変えた**: `GengouCode-NerdFont.zip` は `GengouCode.zip` と
  揃えて**可変 2 本だけ**。欧文の静的 NF 10 面は組まなくなった
  （静的面は JP 面の入力として引き続き組む）。
  `nerdpatch.py` を引数なしで走らせたときの対象も、欧文は可変 2 本に
- 検証: `verify_latin_vf.py` が NF の名前を知り、`check_nerd_font_icons` を
  掛ける。4 本（通常と NF の各 2 本）とも全門番を通過。NF 版は 1 本
  2 分半（インスタンスごとの門番がアイコン 1 万字も歩くため）。
  サイズは各 3.9 MB（見積もりの 3.3 MB より大きいのは CFF2 を
  サブルーチン化していないため）
- CI の `variable + Nerd Font` は、静的面を組まずに可変 2 本へ接ぎ木して
  4 本を検証する形に。`release.yml` は Bold の 2 ジョブが可変フォントと
  その NF 版を組んで検証する（当初は package ジョブが全静的面と並べて
  検証していた。下の「ビルドの簡素化」3 で静的面との比較をやめた）

### 7. `verify_jp.main()` の分解（案 B）

**事実**: `verify_jp.py` は 1,819 行で関数 10 個、うち `main()` が
**1,410 行（77%）**。その中に `check()` が 67 個、`for` が 89 個。

`verifylib.py` 77 関数/最大 262 行）。**構造上の異常はここ 1 か所だけ**。

**ラウンド 12 の指摘 5 件が同じ根から出ています**:

| 指摘 | 起きていたこと |
|---|---|
| 1a | JP 面で合字 61 個が全部死んでいても合格していた（同じ規則が欧文の `main()` にもあり、片方だけ正しかった） |
| 1c | `NF_SYMBOLS` 必須のガードが欧文側だけにあった |
| 2b | 東アジア文字幅の 35 行が `check_widths_by_class` と完全に重複 |
| 2d | `CASES` ループの二重実装 |
| 3a | `check_family_cmap` が CI で一度も走っていなかった |

**合流先は大きい**。`verify_latin.main()` の検査 18 件のうち
**14〜16 件が `verify_jp.main()` の中に双子を持っています**（ファミリー名、
PostScript 名、ウェイト名、usWeightClass、nameID 0、CFF 幅と hmtx、
ベアリングと xMin、インクが送り幅の中、レパートリ、中央配置、ヒント、
GSUB/GPOS の tag、テーブルの有無、`NF_SYMBOLS`）。つまり
**欧文ドライバはほぼ丸ごと二度書きされています**。

**案 B の中身**:
1. 67 検査を名前つき関数に割る
2. うち欧文と重なる 14〜16 本を `verifylib` に上げて 1 本化。
   `verify_latin.main()` はほぼ空になる
3. JP 固有の約 47 本は `verify_jp.py` の module 直下に置く
   （`verifylib` に上げない。3,000 行超に肥大し、JP でしか使わないものが
   混ざるため）

**削減の見積もり 150〜250 行。**

#### 結果（済）

1. `main()` は 47 個の名前つき関数 `check_*(face, check)` の呼び出し列に

2. **双子は 14〜16 組ではなく 5 組でした。** 規則も意味も同じだったのは

   インクが送り幅の中、Nerd Fonts の門番の 5 つだけです。これを `verifylib` に
   上げました（`check_family_names`, `check_weight_class`,
   `check_charstring_metrics`, `check_ink_inside`, `check_nerd_font_icons`）。
   残りは同じ題目でも問いが違います（nameID 0 は JP では Source Han Sans を
   **求め**、欧文では**禁じる**。ヒントの門番は JP だけ合字を見る。
   インク中心の平均は漢字・かなと英数字で対象が違う、など）。**`verify_latin.main()`
   が「ほぼ空になる」ことはありません**
3. 行数は減っていません（`verify_jp.py` 1,819 → 約 1,975 行）。関数ごとの
   前置き（`face` から取り出す 1 行）と区切りの分だけ増えました。狙いは行数
   ではなく、門番どうしが局所変数を共有しない形にすること（`full` が
   コードポイントの集合→グリフ名→箱と 3 度意味を変えていた）です

**示したこと**:
- 分割（1 コミット目）: 全 62 面の検証出力が分割の前後で**バイト単位で同一**
  （`PYTHONHASHSEED=0` で固定。ok 15,182 / skip 12、FAIL はヒントのみ）

### 検証体系（6・7 の結果）

**原則: 門番は配る物だけに掛ける。** 配るのは JP 面（とその NF 版）と、欧文の
可変フォント（とその NF 版）の 2 種類で、`verify.py` はこの 2 種類だけを
`verify_jp.py` / `verify_latin_vf.py` に振り分け、それ以外（欧文の静的面）は
「配布物ではない」と止める。欧文の静的面は JP 面の材料で、その欠陥は
JP 面の門番で捕まる。

- `verify_latin.py` を削除。47 の検査を 1 本ずつ突き合わせ、44 は JP 面側で同じ
  `verifylib` の門番が見ているか、静的面自身のメタデータ（JP 面では
  `build.py` が付け直す）だった。**JP 面側に無かった 3 つを足した**:
  Source Code Pro がインクを持つ字はすべて描ける（`check_donor_draws`。
  それまで JP 面は A〜z しか数えておらず、ギリシャ・キリル・アクセント付きの
  字が空になっても通った）、欧文の字の平均中心（`mean_ink_offset`、
  漢字・かなと並べて）、`ss11` を含む欧文の feature 一覧（`FEATURE_SURFACE`）
- 可変フォント側の重複を解消: `check_ligature_cells` が各位置で見ている合字の
  2 検査を削除、「700 字以上が描ける」は `check_donor_draws` に置換、
  平均中心と feature 一覧は共通のものに
- CI・リリースは静的面を検証しない（CI の Light Italic ジョブが静的面の
  `check_family_cmap` のために Regular Italic も組んでいたのも廃止）
- **示したこと**: 配る 44 面の検証ログを前後で比べ、消えた行は重複と置き換えの
  分だけ、増えた行は新しい門番だけで**すべて ok**、ヒント以外の FAIL は 0

**やらないほうがよいもの**: 箱の計算が 3 通りある件（`build.update_bbox`、
`nerdpatch.update_bbox_after`、`build_latin_vf.master_extents`）。
`update_bbox` は CFF2 を既定位置でしか測らないので、可変フォントに使うと
箱が縮む（4 の実装でもこれを避けた）。
